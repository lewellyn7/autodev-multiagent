# P1-3 向量去重 Spike 报告 (2026-06-14 23:36)

## 背景
- **问题**: 数据库 23.6% project_no 重复率 (1810 条记录 / 1383 个 project_no)
- **假设**: 向量相似度能识别重复项目
- **目标**: 1h spike 验证精度/召回, 给出阈值建议

## 现状摸清
- `vector_store_1024`: 23,203 条 (1024-dim HNSW 索引)
- `vector_store`: 11,369 条 (2560-dim halfvec, 老表, 6-5 之后未更新)
- 当前 production 用 `vector_store_1024` (P0-2 PURE LIFT 后)
- vLLM embedding 服务: 不可用 (host.docker.internal:8000 超时)
- Fallback: TF-IDF → deterministic vector (质量低, 但可跑)

## 实验设计
- 抽样 1000 个最近 vector (按 updated_at DESC)
- 读 1024-dim embedding
- 算 1000×1000 余弦相似度矩阵 (499K 配对)
- 与 projects_cqggzy 关联, 验证 project_no / title / info_type 一致率

## 关键数据

| 阈值 | 配对数 | project_no 一致率 | title 一致率 | info_type 一致率 |
|------|-------|------------------|-------------|-----------------|
| >0.90 | 2,189 (0.4%) | **56.6%** | 70.7% | **93.7%** |
| >0.85 | 2,353 | 53.7% | - | - |
| >0.80 | 2,689 | 47.5% | - | - |
| >0.70 | 4,741 | - | - | - |

## 结论

### 1. 向量相似度能识别部分重复, 但精度不够
- >0.90 时 56.6% project_no 一致 (1240/2189 真重复)
- 还有 605/2189 = 27.6% 假阳性 (高相似但不同 project_no)
- 阈值越严格, 精度越高, 但召回率越低

### 2. ROI 太低
- 真重复 1240 对 / 1000 样本 → 实际 1.6% 重复率
- 6-14 当天 552 条 standardized_all 中, 估计 ~9 条真重复
- 节省 9 条详情抓 × 30s = **4.5 min/周期** (16 min → 15.5 min)
- 投入: 改 db.py / pipeline.py / project_linker.py / UI ≈ 3h
- 收益: 4.5 min/周期 × 7 周期/天 = 31 min/天
- **回本周期: 6 天**, 边际收益太薄

### 3. 需求重定义
- **采集层 URL 已唯一** (URL 是 PK, ON CONFLICT UPDATE), 不需要向量去重
- **项目层 project_no 重复**: 这是 UX 问题, 不是采集问题
  - 同 project_no 出现 N 次 (不同 info_type: 招标公告 + 答疑补遗 + 中标结果)
  - **应该"链接展示"** (1:N 关联), 不是"去重"
  - 当前 `app/utils/project_linker.py` 已有 1:N 关联, **前端可能未用**
- **真重复 (URL 不同, 内容同)**: 占比 < 1%, 不值得做

## 建议: 暂不做 P1-3, 改做 P1-3a "前端项目链接展示"

### P1-3a (建议优先)
- **目标**: 前端把同 project_no 的多条记录合并显示 (主公告 + N 个子公告)
- **代码改动**: 1-2 个前端文件, 后端 project_linker API 已存在
- **耗时**: 1-2h
- **价值**: 用户体验大幅提升 (去重 5-23% 显示)

### P1-3 (原方案)
- **目标**: 向量识别真重复, 自动合并
- **ROI**: 6 天回本, 边际收益薄
- **建议**: **不做** (除非 vLLM 上线后精度大幅提升)
