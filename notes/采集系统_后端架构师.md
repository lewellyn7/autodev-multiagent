# 后端架构梳理

## 技术栈

### Web 框架
- **FastAPI** — 主 Web 框架，提供 REST API + 页面渲染
- **Uvicorn** — ASGI 服务器（支持 reload 开发和多 worker 部署）
- **Jinja2Templates** — 服务端页面渲染（HTML templates）

### 爬虫核心
- **Playwright + playwright-stealth** — 浏览器自动化（渲染 JS 页面、反检测）
- **httpx / aiohttp** — 异步 HTTP 客户端（轻量页面）

### 数据持久化（双库）
- **PostgreSQL 16 + pgvector** — 主数据库，存储采集记录、用户、项目
- **SQLite** — 轻量配置/缓存存储（`tender_scraper.db`）
- **asyncpg** — PostgreSQL 异步驱动（连接池）
- **psycopg2-binary** — PostgreSQL 同步驱动（SQLite 降级路径）
- **Redis 7** — 缓存池（URL 去重、限频、LRU）

### 调度系统
- **APScheduler (BlockingScheduler)** — 独立容器运行，定时触发采集任务（08:00 / 12:00 / 18:00）
- **SmartScheduler** — 内存中动态优先级调度器（5 因子动态评分：来源可信度、截止时间接近度、历史成功率、请求间隔、关键词匹配）

### AI / NLP
- **RAGFlow** — 知识库 + RAG 查询（向量检索）
- **LLM Service** — 大模型摘要/分类（httpx 调用 vLLM HTTP API）
- **jieba** — 中文分词（关键词匹配）
- **numpy** — 向量计算（pgvector + TF-IDF）

### 监控与日志
- **Loguru** — 结构化日志（文件轮转）
- **Prometheus Client** — 指标暴露（`/metrics`）
- **Audit Log** — 安全审计（采集开始/成功/失败事件）

### 其他
- **Pydantic v2** — 数据验证与序列化
- **Pydantic Settings** — 环境变量配置管理
- **bcrypt** — 密码哈希
- **pytest + pytest-asyncio** — 测试框架
- **Docker + docker-compose** — 容器化部署

## 核心模块

### `app/core/harvest/smart_scheduler.py` — 智能调度引擎
Phase 1 核心，替代了旧版简单的 `asyncio.gather`。

**5 因子动态优先级：**
1. `source_weight` — 来源可信度（cqggzy=1.0, ccgp=0.9）
2. `urgency_deadline` — 截止时间紧迫度（指数衰减，越接近越高）
3. `historical_success` — 该来源历史成功率
4. `adaptive_interval` — 距离上次访问的时间间隔（防封禁）
5. `keyword_match_score` — 关键词匹配得分

**自适应间隔管理：** `AdaptiveIntervalManager` 维护每个站点的度量数据（响应时间、成功率、ban 状态），动态调整采集间隔。

---

### `app/crawlers/base.py` — 爬虫基类
所有爬虫继承 `BaseCrawler`：
- `_mark_visited()` — 异步线程安全 URL 去重
- `_extract_field()` / `_extract_field_by_kw()` — 正则/关键词字段提取
- `_extract_contact_info()` / `_extract_attachments()` / `_extract_budget()` / `_extract_deadline()` — 通用详情提取
- `_parse_date()` / `_parse_datetime()` — 日期解析（支持中文格式）
- `fetch_details_batch()` — 并行批量采集（Semaphore 控制并发）
- `_fetch_with_retry()` — 指数退避重试

子类只需实现 `fetch_list()` 和 `fetch_detail()` 两个抽象方法。

---

### `app/core/browser.py` — StealthBrowser
Playwright 封装，反检测配置：
- 伪造 `navigator.webdriver`、`navigator.plugins`、`navigator.hardwareConcurrency`
- Canvas / WebGL 随机噪声
- 浏览器指纹随机化
- User-Agent 轮换
- 隐式随机等待（`random_delay`）

### `app/database/db.py` — 双库适配

- PostgreSQL：`psycopg2.ThreadedConnectionPool`（10 连接）
- SQLite：原生 `sqlite3`（配置/缓存降级）

### `app/scheduler.py` — APScheduler 调度器
独立容器运行，与 Web 服务完全解耦：
- `BlockingScheduler`（阻塞模式，主进程运行）
- `CronTrigger(hour="08,12,18", minute="0")` — 每天 3 次
- `misfire_grace_time=3600` — 小时级容忍延迟
- 调用 `main.run_collection()` 执行采集
- 审计日志写入（crawl_started / completed / failed）

## 调度机制

### 定时采集（APScheduler）
```
触发时间：每天 08:00 / 12:00 / 18:00（Asia/Shanghai）
入口函数：scheduler.job_run_collection()
执行流程：
  1. 写审计日志 EVENT_CRAWL_STARTED
  2. asyncio.run(run_collection())  → main.py
     - 启动 StealthBrowser
     - 创建 CQGGZYCrawlerV2
     - 采集列表页 → 过滤关键词 → 批量采集详情页
     - TenderFilter 关键词匹配
     - 结果写入 output/latest.json
  3. 写审计日志 EVENT_CRAWL_COMPLETED / EVENT_CRAWL_FAILED
```

### 动态优先级调度（SmartScheduler）
运行在 `main.py` 的采集流程内部：
- 接收 `CrawlTask` 列表（包含静态优先级 + URL）
- 5 因子动态评分 → `priority_dynamic`
- 按优先级排序 → 依次调度执行
- `AdaptiveIntervalManager` 控制请求间隔（防止封禁）
- 失败重试（最多 3 次，指数退避）

## 架构优缺点

### 优点

1. **模块化清晰** — `crawlers/` 继承基类复用逻辑，`services/` 分离业务关注点，`repositories/` 封装数据访问
2. **反检测能力** — StealthBrowser + anti_detect 子系统（TLS 指纹、Canvas、WebGL、行为模拟）有效对抗网站反爬
3. **智能调度** — SmartScheduler 5 因子动态优先级，相比固定间隔采集更高效、更安全
4. **双库灵活** — PostgreSQL（主数据）+ SQLite（轻量配置），支持降级
5. **RAG 生态** — 向量搜索 + LLM 摘要 + 投标人资质匹配，构建了完整的 AI 分析 pipeline
6. **Docker 生产就绪** — docker-compose 定义了 Web + Redis + Postgres + Scheduler 四服务分离
7. **审计日志** — 采集开始/成功/失败事件完整记录，便于问题追溯

### 缺点

1. **调度器与 Web 耦合** — `scheduler.py` 直接 import `main.run_collection()`，虽然容器解耦了进程，但代码层面仍有直接依赖，scheduler 重构时应考虑调用独立的采集 API 而非直接 import
2. **双库维护成本** — PostgreSQL + SQLite 两套 ORM 并存，Repository 模式不够彻底，部分模块直接写 SQL 字符串（`db.py` 中有大量 `cur.execute(f"...")`）
3. **URL 去重局限性** — `BaseCrawler._visited_urls` 是内存 `Set`，分布式多实例部署时会失效；应迁移到 Redis Set
4. **async/sync 混用** — 部分模块用 `asyncpg`（async），部分用 `psycopg2`（sync），缺乏统一抽象；`BaseCrawler` 是 sync 方法在 async context 中被调用时存在风险
5. **Schema 膨胀** — `models/schemas.py` 单文件承载了所有 Pydantic 模型（用户/项目/收藏/通知...），超过 600 行，违反单一职责
6. **配置分散** — `.env`、`.env.example`、`.env.production`、`config/settings.py` 多处配置源，缺少统一的配置校验层
7. **测试覆盖率不足** — 项目有 `tests/` 目录但质量存疑，critical path（采集流程、调度）缺少集成测试
8. **Scheduler 单点** — `BlockingScheduler` 单进程，misfire 时虽有 1 小时容错但无高可用机制；如需精度应迁移到分布式调度（APScheduler + Redis 或 Celery）
9. **CORS/CSRF 配置** — CSRF middleware 被注释禁用，依赖 Session Token header 认证，安全性依赖实现细节而非框架保障
